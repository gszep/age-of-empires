## Original findings (resolved)

### 1. P1 — HUD teardown can delete units without a player response

**Locations:** `src/view/hud.ts:183–185` (`destroy`),
`src/main.ts:972–980` (`remove`), `src/main.ts:1908–1910` (presentation rebuild).

`destroy()` resolves a pending confirmation with `false`. The Delete handler
interprets `false` as the player choosing No, which intentionally deletes the
unflagged members of a mixed selection. A same-match presentation rebuild—used
by view hot reload—therefore sends a destructive public command without a click
or key response. The `game !== match` guard does not help because this rebuild
preserves the simulation object.

**Reproduction:** start a paused imported match; select the player's town center
and a villager; press Delete; leave the dialog open; invoke the existing
`rebuildPresentation()` entrypoint used by HMR. Before rebuilding, the villager
is alive at 25 HP. Afterwards it is absent from the live debug entity reply;
the town center remains at 2400 HP. The probe only stages the initial snapshot
and calls the real presentation lifecycle; it does not delete the villager
itself.

**Required change:** distinguish lifecycle abort from an explicit No. Teardown
must settle/discard the pending operation without invoking either deletion
branch. Preserve the existing deliberate No behaviour for mixed selections.
Add a same-match rebuild regression that asserts the simulation checksum and
entity membership remain unchanged.

### 2. P2 — notification background disappears at the end of the fade

**Location:** `src/view/style.css:250–251`.

The Surround has `z-index: -1`, while `.owned-notifications` removes the parent's
transform. During the fade, opacity below one creates a stacking context, so
the background can appear. At opacity one the parent has no stacking context;
its negative-z child falls behind the battlefield. Imported notifications thus
lose their background precisely when they reach their stable visible state.

**Reproduction:** in the real imported HUD at 1280×800, show a message and wait
for computed opacity one. Place an opaque diagnostic battlefield plane behind
the HUD to avoid animation changing the measurement. Sample an empty centre
portion of the panel at screen (113,160). The screenshot readback is sRGB:

| Condition | RGBA bytes |
|---|---|
| Current CSS, fully visible message | 240, 240, 240, 255 |
| Only add `isolation: isolate` to the message parent | 78, 76, 73, 255 |
| Explicitly hide the Surround | 240, 240, 240, 255 |

The unmodified result is exactly the no-background result. This is a layering
defect, not a reference-colour calibration dispute.

**Required change:** give the message panel a persistent stacking context, or
place background/text on explicit nonnegative layers. Add a browser check that
measures background contribution after opacity has reached one, not merely the
presence of nine DOM cells and background-image URLs.
